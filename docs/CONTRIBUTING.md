# Руководство по работе с репозиторием

## Общие принципы

- Все изменения проходят через Pull Request (PR). Пушить напрямую в `main` запрещено.
- Работа происходит на ветке `dev`, открывать PR на `main` желательно только через администратора репозитория.
- Перед началом работы обновите локальный `dev` (`git pull origin dev`), чтобы избежать конфликтов.
- Перед пушом не забудьте прогнать линтер `prettier --write "**/*.{md,mdx,yml,yaml,json}"`, `prettier --check "**/*.{md,mdx,yml,yaml,json}"`

## Процесс работы

1. Создайте новую ветку от `dev`.
2. Внесите изменения с учетом стандартов ниже.
3. Обновите документацию и тесты, если они затрагиваются вашими изменениями.
4. Убедитесь, что локально проходят проверки и сборка.
5. Откройте PR и отправьте его на ревью, запросив необходимые approve'ы.

## Именование веток

- Формат: `тип/номер_ДЗ-описание`
- Примеры: `docs/HW1-rules`, `fix/HW2-form`
- Допустимые типы: `feature`, `fix`, `docs`, `chore`, `refactor`.

## Стиль коммитов

- Используем схему [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/).
- Структура сообщения: `<тип>(контекст?): <краткое описание>`
- `тип`: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
- В теле коммита описывайте, что и зачем изменилось, перечисляйте важные детали.

## Политика ревью и approve'ов

- Для каждого PR обязательно минимум **четыре approve-а** от участников команды.
- Изменения, затрагивающие архитектуру или публичные интерфейсы, требуют дополнительного согласования с техлидом.
- После получения всех approve'ов автор отвечает за squash и merge/реализацию договоренного сценария слияния.

## Дополнительные рекомендации

- Соблюдайте стиль кода и форматирование, принятые в проекте (например, через eslint/formatter команд проекта).
- Поддерживайте историю коммитов чистой: не оставляйте `WIP`-коммиты в PR.
- Перед мержем обновите ветку до свежего `dev` (`git rebase dev` по договоренности).
